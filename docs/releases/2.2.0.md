# Nexori 2.2.0

Nexori 2.2.0 adds backend-driven matchmaking, backend result reporting, manual game ownership through `rulesEngineId`, and a cleaner public API for third-party rules mods.

This release matters most for:

- server owners who want external matchmaking
- backend developers implementing `/nexori/sync` and `/nexori/results`
- minigame/rules mod developers integrating directly with Nexori

## Highlights

### Backend-Driven Matchmaking

Queues can now use `BACKEND_DRIVEN`, which means Nexori keeps the players queued while your backend decides match assignments.

Your backend can now:

- inspect queue snapshots through `/nexori/sync`
- choose which players should be matched
- choose which arena should be used
- receive launch ACKs back from Nexori

Nexori still owns validation, travel, instance launch, and secure match handoff.

[Read the sync endpoint docs](/backend/sync-endpoint)

### Backend Result Reporting

Completed matches can now be reported to your backend through `POST /nexori/results`.

This is event-driven, not a heartbeat. It is meant for final match results, player outcomes, and optional minigame-specific `customData`.

Arena servers can use:

- `syncEnabled=false`
- `resultReportingEnabled=true`

That means result reporting can work even when the arena server is not participating in matchmaking heartbeat.

[Read the results endpoint docs](/backend/results-endpoint)

### Backend Configuration In Game

Nexori Menu V2 now includes backend configuration and a backend terminal view, so operators can configure the backend and inspect request health directly in game.

![Nexori backend configuration UI](/images/backend-matchmaking-ui.png)

This release adds in-game control over:

- backend origin URL
- API key / server token
- sync interval
- result reporting
- result retry interval
- region
- request timeout

[Read backend configuration](/backend/configuration)

### Manual Game Ownership

Manual games now support `rulesEngineId`.

This lets multiple third-party rules mods live on the same arena server without every mod trying to control every manual match. A rules mod can inspect the active match, verify `rulesEngineId`, and stay passive unless the match belongs to it.

[Read rules mod ownership](/concepts/rules-mod-ownership)

### Public Minigame API

The public minigame API was expanded into a cleaner rules-mod integration surface.

For new rules mods, the recommended flow is:

- detect the active match
- verify ownership
- wait for placement completion
- set player outcomes during the match
- optionally mark logical spectators
- return players separately
- submit the final result once the match is complete

[Read public API methods](/public-api/methods)

[Read the recommended flow](/public-api/recommended-flow)

## What Changed For Backend Developers

Nexori now exposes two backend contracts:

- `/nexori/sync`
  Use this for backend-driven matchmaking heartbeat, queue snapshots, arenas, active matches, assignments, and assignment ACKs.
- `/nexori/results`
  Use this for final match result reporting, including `rulesEngineId`, player outcomes, and `customData`.

If you are implementing the backend side, start here:

- [Backend configuration](/backend/configuration)
- [Sync endpoint](/backend/sync-endpoint)
- [Results endpoint](/backend/results-endpoint)

## What Changed For Minigame Mod Developers

The old public API still has compatibility paths, but the new recommended API separates responsibilities more clearly.

The main ideas are:

- set outcomes during the match instead of waiting until the end
- keep spectator state separate from return-to-lobby
- submit the final result once, at the end
- attach minigame-specific stats through `customData`

If you are building a rules mod, start here:

- [Minigame API](/public-api/minigame-api)
- [Methods](/public-api/methods)
- [Recommended flow](/public-api/recommended-flow)

## Compatibility Notes

- Existing queues without an explicit matchmaking mode are treated as `LOCAL_FIFO`.
- Existing 2.1.0 mods using `findActiveMatchId(...)`, `findActivePlayerUuid(...)`, `findMatchPlacementState(...)`, or `findMatchResolutionTriggerId(...)` remain compatible.
- `resolvePlayerOutcome(...)` still exists as a deprecated compatibility path, but new mods should use the separated API methods.
